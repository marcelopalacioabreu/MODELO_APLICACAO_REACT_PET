Banco de dados e persistência

Banco: MongoDB via mongoose. Modelos Mongoose em src/models. Persistência está documentada por schemas nos arquivos de modelo; operações CRUD são feitas a partir dos controllers e services.

Coleções / Modelos principais

User, Role, Permission, Pet, Tutor, Location, MedicalRecord, InventoryTransaction, FeedPost, Campaign, Bed, Appointment, AuditLog, etc.

Migrations & Seeds

Não há framework de migrations formal (ex: migrate, TypeORM). Em vez disso, há scripts ad-hoc em backend/scripts/ que fazem correções, seeds e transformações (ex: migrate_beds_array.js, seedAdmin.js, runIntegrity.js). Para aplicar uma migração, execute:

node scripts/migrate_beds_array.js

Persistência adicional

  • Redis é usado para sessões ativas, cache e integração com Socket.IO (ver src/services/redisService.js).
  • File uploads via multer, imagens processadas com sharp.
  • Sessions & Tokens: JWT para access e refresh tokens; sessão ativa guardada em Redis com chave active_session:userId.

Acoplamento e persistência — análise

  • O projeto usa controllers diretamente ligados a modelos Mongoose — acoplamento direto (controller -> model). Isso facilita entendimento, mas dificulta testes unitários isolados.
  • Serviços transversais (Redis, file storage) ficam em `src/services`, o que melhora reutilização; porém alguns controllers importam modelos e serviços diretamente, criando acoplamento forte.
  • Não há camada clara de repositório/DAO — extração de queries para services/repositories reduziria acoplamento.
  • Migrations são scripts ad-hoc; isso funciona, mas torna rastreabilidade e reversão mais difíceis. Recomendação: adotar um sistema de migrations para Mongo (migrate-mongo ou um processo baseado em change-sets) e versionamento das mudanças.

Como inspecionar

  1. Abra backend_structure.mmd para editar o mermaid fonte.
  2. Abra este arquivo index.html no navegador para visualizar.
  3. Para rodar scripts/migrations: no container/ambiente com Mongo conectado, executar `node scripts/.js`.
